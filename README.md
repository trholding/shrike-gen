# shrike-gen

CLI project scaffolding and build toolchain for Vicharak's Shrike FPGA Board and the **Renesas SLG47910V** (ForgeFPGA).

Designed to replace the Go Configure Software Hub GUI with a fully scriptable, terminal-driven workflow. Write Verilog (in future VHDL), edit pin constraints, type `make`, get bitstreams.

**Status:** Alpha - Supports only simple projects now

**License:** MIT 

---

## Motivation

The Go Configure Software Hub GUI is the official path to programming the SLG47910V, but it makes rapid iteration slow! Every change requires navigating the GUI's IO Planner, clicking through regeneration steps, and waiting on a heavyweight desktop app. `shrike-gen` decouples the entire flow from the GUI: project creation, `.ffpga` generation, IO spec compilation, synthesis, place-and-route, and bitstream packaging are all driven from the command line via `make`.

The `.ffpga` files and all three bitstream formats (`MCU`, `OTP`, `FLASH_MEM`) are generated byte-compatible with the GUI. You can still open the project in the GUI, but why would you?

## Prerequisites / Requirements

The following tools must be installed and on the paths the Makefile expects:

| Tool | Purpose | Default path |
|---|---|---|
| **Go Configure Software Hub** | Provides `yosys`, `verilator`, `eda-placer` | `/opt/go-configure-sw-hub/bin/external/` |
| **Python 3.8+** | Runs all `gen_*.py` scripts | `python3` on `$PATH` |
| **GNU Make** | Drives the build | `make` on `$PATH` |

All three binary tools (`yosys v59`, `verilator`, `eda-placer v23`) ship with the Go Configure Software Hub installation. No separate tool installation is required.

## Quick start

### 1. Clone and (optionally) create the `shrike-gen` symlink

```bash
git clone https://github.com/trholding/shrike-gen.git
cd shrike-gen

make init          # creates ./shrike-gen → shrike_gen/shrike-gen.py (optional)
```

`make init` is optional. It lets you run `./shrike-gen ProjectName` directly. Without it, `make project` is the only entry point needed.

Okay ./shrike-gen is a way of saying thank you to Vicharak for the Shrike-lite board they sent me :)

### 2. Create a project

```bash
# Either syntax works:
make project Blink
make project NAME=Blink

# Or, if you ran make init:
./shrike-gen Blink
```

This creates:

```
Blink/
├── Makefile              ← copied from workspace root (project-mode build)
├── shrike.mk             ← PROJECT=Blink  TOP=Blink
├── Blink.ffpga         ← GUI-compatible project file (auto-regenerated)
├── io_map.pcf            ← pin constraints — edit this
├── ffpga/
│   ├── src/
│   │   └── main.v        ← top-level Verilog — edit this
│   └── build/
│       ├── floorplanspec.fp    ← fixed device descriptor (do not edit)
│       └── io_spec_in.txt      ← generated from io_map.pcf (do not edit)
└── shrike_gen/           ← generator scripts (copy of workspace shrike_gen/)
```

### 3. Write your design

Edit:
```
Blink/ffpga/src/main.v    # Verilog source
Blink/io_map.pcf          # pin assignments
```

**`io_map.pcf` syntax:**

Similar to nextpnr

```
set_io <signal_name>  <assignment>
```

GPIO pins are referenced by package number. OE (output enable) and IN (input) variants follow the `PIN_N_OE` / `PIN_N_IN` convention:

```
set_io clk     CLK         # external clock input
set_io LED     PIN_7       # output value on pin 7
set_io LED_en  PIN_7_OE    # output enable on pin 7 — drive HIGH to enable
set_io clk_en  OSC_EN      # oscillator enable
```

Available GPIO ranges: `PIN_1`–`PIN_9` (east edge), `PIN_13`–`PIN_20` (west edge), `PIN_23`–`PIN_24` (east edge).

For the full pin reference:

```bash
python3 Blink/shrike_gen/gen_io_spec.py --list-pins
```

### 4. Build

```bash
cd Blink
make              # update (regenerate .ffpga + io_spec_in.txt) then full build
```

Bitstreams land in `ffpga/build/bitstream/`:

```
FPGA_bitstream_MCU.bin        ← for MCU-mode programming
FPGA_bitstream_OTP.bin        ← for OTP programming
FPGA_bitstream_FLASH_MEM.bin  ← for flash-memory programming
```

## Build targets

### Workspace (run from the repository root)

| Target | Description |
|---|---|
| `make init` | Create `./shrike-gen` symlink (optional convenience) |
| `make project NAME=X` | Create a new project skeleton named `X` |
| `make project X` | Same, positional form |
| `make list` | List existing projects in this workspace |
| `make help` | Show workspace help |

(Note: Replace X with actual project name)

### Project (run from inside a project directory)

| Target | Description |
|---|---|
| `make` | `update` then `build` (full rebuild) |
| `make update` | Regenerate `.ffpga` and `io_spec_in.txt` from `io_map.pcf` |
| `make build` | `lint` → `synth` → `pnr` → `collect` (skip update) |
| `make lint` | Verilator lint only |
| `make synth` | Yosys synthesis only |
| `make flash` | Flash the project bin to FPGA |
| `make clean` | Remove all build outputs (keeps source and constraints) |
| `make help` | Show project help |

The Makefile is **role-aware**: it detects whether it is in a workspace or project directory. Workspace targets (`init`, `project`) are unavailable inside a project, and project build targets are unavailable at the workspace root.

If `mpremote` is already on your system (system package, `pipx`, `uv`,
or a prior `--user` install) it is detected and reused. Otherwise it is
installed into the **Python user site** (`~/.local`) — no virtualenv, and
system packages are left untouched. On PEP 668 distros (Ubuntu 24.04,
Debian 12+) the install retries with `--break-system-packages`; paired
with `--user` this only writes to `~/.local`, not system site-packages.

`make init` is optional — `make flash` installs `mpremote` on first use
anyway. Provision it explicitly any time with:

```
make mpremote-install
```

Overrides:

| Variable        | Effect                                                       |
| --------------- | ------------------------------------------------------------ |
| `MPREMOTE=...`  | Use a specific mpremote (e.g. a venv's `bin/mpremote`)       |
| `PYTHON=...`    | Use a specific interpreter for detection/install            |
| `AUTO_INSTALL=0`| Never auto-install; error and point at `make mpremote-install` |

`pip` itself must be present (`python3-pip`); it can't be bootstrapped
without root, so install it once if missing.

## Flashing

`make flash` copies a bitstream onto the RP2040/RP2350 and calls the
Shrike MicroPython `shrike.flash()` routine to configure the FPGA. This
requires the **Shrike MicroPython UF2 already on the MCU** (see the
getting-started guide).

```
make flash                          # current project, MCU bitstream
make flash FROM=Blink2              # flash a sibling project's bitstream
make flash VARIANT=FLASH_MEM        # pick a bitstream variant
make flash PORT=/dev/ttyACM0        # target one board when several are attached
make flash BITSTREAM=/path/to/x.bin # flash an arbitrary file
```

Resolution precedence: an explicit `BITSTREAM=` wins; otherwise `FROM=<name>`
selects the sibling project `../<name>`; otherwise the current project.
`FROM` assumes the other project is a sibling whose directory name matches
its project name (true for anything `shrike-gen` scaffolds) — use
`BITSTREAM=` for anything else.

> **OTP is irreversible.** `make flash VARIANT=OTP` refuses unless you add
> `I_KNOW_OTP_IS_FOREVER=1`. Verify against GUI-generated output and test on
> a non-OTP target first.

### Custom top-level module name

By default the top-level module name matches the project name. Override with `--top`:

```bash
python3 shrike_gen/shrike-gen.py Blink --top blink_top
```

### Custom parent directory

```bash
python3 shrike_gen/shrike-gen.py Blink --dir ~/fpga/projects
```

### Overwrite an existing project

```bash
make project Blink --force
# or
python3 shrike_gen/shrike-gen.py Blink --force
```

### Opening the project in the GUI

The generated `Blink.ffpga` is a bare minimum project file that the Go Configure Software Hub can read. Open it normally, then within open the main.v file. The IO Planner will reflect your `io_map.pcf` assignments.

## How it works

`shrike-gen` implements the basic Go Configure Software Hub project format and toolchain invocation with a Makefile and Python:

- **`gen_ffpga.py`** — produces a valid minimal `.ffpga` project XML file with correct device constants for the SLG47910V Rev BB 
- **`gen_io_spec.py`** — parses the nextpnr style PCF constraint file and outputs the `io_spec_in.txt` format consumed by `eda-placer`, and the `<io-spec-tool>` XML block embedded in the `.ffpga` file.
- **`gen_fpga_data.py`** — constructs the `FPGA_DATA` base64 blob passed to `eda-placer` as its primary input.
- **`gen_bitstreams.py`** — reads `FPGA_bitstream_AXI.log` from `eda-placer` and produces all three bitstream `MEM`, `MCU` and `OTP` variants. All formats verified byte-compatible with GUI-generated output.

The build pipeline is: **Verilator lint** → **Yosys synthesis** (EDIF netlist) → **eda-placer v23 PnR** → **bitstream collection**.
